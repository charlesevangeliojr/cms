================================================================================
CMS PROJECT — FOLDER STRUCTURE & GUIDE
================================================================================
 PURPOSE OF THIS FILE
 --------------------
 This file explains, in plain language, WHERE each part of the project lives,
 WHY it exists (its purpose), and WHAT RULES to follow when adding new code.
 Read it before adding files so the project stays organized.

 PROJECT OVERVIEW
 ----------------
 This is a Laravel 11 CMS (Content Management System) template with two sides:

   1. FRONTEND  — Public static landing pages (Home, About, ...).
                  Data is NOT from the database yet. It comes from a
                  CONTROLLER using MOCK DATA (hard-coded arrays), so pages
                  can be built before the database/models exist.

   2. BACKEND   — The /admin area (login + dashboard).
                  Reads/writes the DATABASE. Protected by login.

 Request flow (how a page is born):

   Browser URL
       -> routes/web.php          (maps URL to a controller method)
       -> app/Http/Controllers/*  (gets the data — mock or from DB)
       -> resources/views/**      (Blade template renders HTML)
       -> public/ assets          (images/CSS/JS served by the browser)

================================================================================
PUBLIC/  — WEB ROOT
================================================================================
 PURPOSE: The ONLY folder the web server exposes by URL.
          If a file is not here, the browser cannot load it directly.

 public/index.php
   PURPOSE: Front controller. Every HTTP request enters the Laravel app
            through this file first.

 public/frontend/
   PURPOSE: Static assets used ONLY by the frontend (landing pages).
            Checked into git. The CMS never writes here at runtime.

   RULE: One subfolder per page/section when its assets arrive.
         Naming follows the page. Current/expected subfolders:
           about-us/     images for the About page
           background/   page/section background images
           banners/      frontend banner images
           favicon_io/   favicons / app icons
           home/         images for the Home page
           products/     static product images shown on frontend
           projects/     static project images shown on frontend

 public/uploads/
   PURPOSE: Storage for files UPLOADED through the CMS by an admin
            (product photos, banners, project images, resource files, ...).
            Served publicly via URL.

   RULE: Written by the app at runtime. New uploads are NOT committed to
         git (only .gitkeep stays tracked).
   RULE: One subfolder per upload type/module — NOT fixed in stone.
         Example from the REALTECH project:
           banners/      banner images uploaded via CMS
           products/     product images uploaded via CMS
           projects/     project images uploaded via CMS
           resources/    resource files uploaded via CMS
         If this project has different modules (careers, promos, teams...),
         add/rename subfolders to match — e.g. uploads/careers/.

 public/build/
   PURPOSE: Compiled CSS/JS assets generated by Vite (via `npm run dev`
            or `npm run build`). Do NOT edit files here by hand — they
            are overwritten on every build.

 QUICK ANSWER:
   Landing-page image?            -> public/frontend/<page>/
   File uploaded through the CMS? -> public/uploads/<type>/

================================================================================
APP/  — APPLICATION LOGIC (PHP)
================================================================================
 PURPOSE: All the PHP code that runs on the server. Never served as
          static files — only executed by Laravel.

 app/Http/Controllers/Controller.php
   PURPOSE: Abstract base class all controllers extend. Currently empty;
            shared controller logic can be added here later.

 app/Http/Controllers/AuthController.php
   PURPOSE: Handles ADMIN LOGIN / LOGOUT for the backend.
     - showLogin()  -> renders the login form (or redirects to dashboard
                       if already logged in)
     - login()      -> validates email/password, attempts auth,
                       regenerates the session, redirects to dashboard
     - logout()     -> logs out, invalidates the session, redirects
                       to the login page
   ROUTES: /admin/login (GET/POST), /admin/logout (POST)

 app/Http/Controllers/PageController.php
   PURPOSE: Serves the FRONTEND pages (Home, About) with MOCK DATA.
            This is the most important controller to understand —
            see the dedicated section below.

  app/Http/Controllers/DashboardController.php
   PURPOSE: Serves the ADMIN DASHBOARD (/admin/dashboard, login required).
     - index()  -> gathers real stats (total users, 5 most recent users,
                   uploaded-file count, frontend page list, Laravel/PHP
                   versions, env, DB driver, timezone) and passes them to
                   the backend.dashboard view as $totalUsers, $recentUsers,
                   $uploadCount, $pages, $pageCount, $laravelVersion,
                   $phpVersion, $environment, $dbDriver, $timezone.

  app/Models/User.php
   PURPOSE: Eloquent model for the `users` table. Used by the backend
            login system (Auth).

 app/Providers/AppServiceProvider.php
   PURPOSE: Service provider for app-wide boot/setup logic.

--------------------------------------------------------------------------------
 CONTROLLER & MOCK DATA  — app/Http/Controllers/PageController.php
--------------------------------------------------------------------------------
 WHY MOCK DATA?
   The landing pages are built BEFORE the database tables/models for
   content exist. Instead of hard-coding text inside Blade templates
   (which is messy and hard to swap later), the data lives in the
   CONTROLLER as plain PHP arrays. When real models arrive later, only
   the controller changes — the Blade files keep receiving the SAME
   variables ($site, $nav, $page) and need no edits.

 HOW IT WORKS (step by step):

   1. private function mockData(): array
        Returns one big associative array holding ALL page data:
          'site'  -> site-wide info (name, tagline)   -> used by
                     header/footer partials
          'nav'   -> menu items (label, url)          -> used by
                     header/footer partials
          'home'  -> Home page data (heading, text,
                     cta, features[])                 -> used by
                     pages/home + sections/features
          'about' -> About page data (heading, text,
                     cta, stats[])                    -> used by
                     pages/about + sections/stats

   2. public function home()
        Calls mockData(), then returns the view with THREE variables:
          $site -> site info
          $nav  -> menu items
          $page -> the 'home' slice of the mock data
        View returned: frontend.pages.home

   3. public function about()
        Same pattern, but $page = the 'about' slice.
        View returned: frontend.pages.about

   THE CONTRACT (important):
     Every frontend controller method must pass at least:
       $site  (array)  — site name/tagline for header & footer
       $nav   (array)  — navigation links for header & footer
       $page  (array)  — this page's content (heading, text, cta, blocks)
     Partials may fall back to defaults (??), but sections expect their
     arrays ($features, $stats) — always pass them inside $page.

   HOW TO ADD A NEW PAGE:
     1. Add a key to mockData() — e.g. 'services' => [...]
        (heading, text, cta, plus any block arrays)
     2. Add a method — e.g. public function services()
        that returns view('frontend.pages.services',
        ['site'=>..., 'nav'=>..., 'page'=>$data['services']])
     3. Register the route in routes/web.php
     4. Create resources/views/frontend/pages/services.blade.php
     5. Add the link to the 'nav' array in mockData() so it appears
        in the header/footer

   HOW TO SWAP TO REAL DATA LATER (no Blade changes):
     Replace the mock array with Eloquent queries inside the method:

       public function home()
       {
           return view('frontend.pages.home', [
               'site' => Setting::first()->toArray(),   // real DB
               'nav'  => NavItem::ordered()->get(),      // real DB
               'page' => Page::where('slug','home')->first()->toArray(),
           ]);
       }

     Because the variable NAMES stay the same, every Blade file
     (pages, partials, sections) continues to work untouched.

   MOCK DATA SHAPE (current, for reference):
     site: { name, tagline }
     nav:  [ { label, url }, ... ]
     home: { heading, text, cta:{label,url},
             features:[ {title,text}, ... ] }
     about:{ heading, text, cta:{label,url},
             stats:[ {value,label}, ... ] }

================================================================================
ROUTES/  — URL MAP
================================================================================
 PURPOSE: Decides which controller/view handles each URL.

  routes/web.php   (current map — frontend is PUBLIC, no login needed)
    GET  /                 -> PageController@home       name: home
                             (public landing page — no auth)
    GET  /about            -> PageController@about      name: about
                             (public page — no auth)
    GET  /home             -> redirect 301 -> /         (legacy URL)
   GET  /admin/login      -> AuthController@showLogin  name: login
   POST /admin/login      -> AuthController@login      name: login.attempt
   POST /admin/logout     -> AuthController@logout     name: logout
    GET  /admin/dashboard  -> DashboardController@index      name: dashboard
                             (inside 'auth' middleware — login required.
                              Passes $totalUsers, $recentUsers, $uploadCount,
                              $pages/$pageCount, system info to the view.)
   GET  /login            -> redirect 302 -> /admin/login   (legacy URL)
   GET  /dashboard        -> redirect 302 -> /admin/dashboard (legacy URL)

 routes/console.php
   PURPOSE: Artisan console commands (cron-like tasks).

================================================================================
RESOURCES/VIEWS/  — BLADE TEMPLATES (HTML)
 PURPOSE: Every file that produces the HTML sent to the browser.
          Split into FRONTEND (public site), BACKEND (admin), and
          shared EXTRAS (components, errors).

--------------------------------------------------------------------------------
 frontend/  — STATIC LANDING PAGES (not CMS-managed)
   The public landing page markup. Pages here are STATIC: data does NOT
   come from the database. Each page's data comes from PageController
   as MOCK data (see the controller section above).
   When real models exist later, only the controller changes — the
   blades keep using the same $site / $nav / $page variables.

   CHOP-CHOP RULE: never put a whole page in one file. Split into:

     layouts/    Page shells (html/head/body, @yield sections).
                 layouts/app.blade.php is the single frontend shell;
                 it @includes the header and footer partials and
                 @yield('content') for the page body.

     pages/      One file per URL (home.blade.php, about.blade.php).
                 Each page @extends a layout and fills @section blocks.

     partials/   Small reused chunks included by layouts/pages.
                   header.blade.php = top navigation bar
                   footer.blade.php = site footer
                 Both read $site and $nav from the controller.

     sections/   Page content blocks fed by controller data.
                   features.blade.php  expects $features
                     -> item shape: { title, text }
                   stats.blade.php     expects $stats
                     -> item shape: { value, label }
                 A page includes a section like:
                   @include('frontend.sections.features',
                            ['features' => $page['features'] ?? []])

   CURRENT MAP (how the pieces connect):

      routes/web.php
        /      -> PageController@home   (PUBLIC landing page, no login)
                   -> frontend/pages/home.blade.php
                        @extends frontend/layouts/app.blade.php
                          @include frontend/partials/header  ($site,$nav)
                          @yield('content')
                            <x-card> heading/text/cta  (from $page)
                            @include frontend/sections/features ($features)
                          @include frontend/partials/footer  ($site,$nav)

       /about -> PageController@about
                   -> frontend/pages/about.blade.php
                        @extends frontend/layouts/app.blade.php
                          @include frontend/partials/header  ($site,$nav)
                          @yield('content')
                            <x-card> heading/text/cta  (from $page)
                            @include frontend/sections/stats ($stats)
                          @include frontend/partials/footer  ($site,$nav)

   FILE INVENTORY:
     frontend/layouts/app.blade.php     frontend shell (head, @yield)
     frontend/partials/header.blade.php top nav (reads $site, $nav)
     frontend/partials/footer.blade.php footer (reads $site, $nav)
     frontend/pages/home.blade.php      Home page body
     frontend/pages/about.blade.php     About page body
     frontend/sections/features.blade.php  feature cards (expects $features)
     frontend/sections/stats.blade.php     stat cards   (expects $stats)

--------------------------------------------------------------------------------
 backend/  — CMS FUNCTIONS (admin area)
   Everything behind /admin login: dashboard, content management,
   settings — anything that reads/writes the DATABASE.

   CURRENT MAP:
     layouts/sidebar.blade.php   Admin shell: html head + left sidebar
                                 (Dashboard link on top, Logout pinned at
                                 the bottom) + header + @yield('content')
     partials/sidebar.blade.php  The sidebar nav itself (included by
                                 layouts/sidebar)
      dashboard.blade.php         Extends backend.layouts.sidebar. Data comes
                                  from DashboardController@index (NOT static):
                                  welcome hero (date, user name/email, View
                                  Website / About buttons), 4 stat cards
                                  (Total Users, Frontend Pages, Uploaded
                                  Files, Framework/PHP versions), Recent
                                  Users table (avatar initial, name, email,
                                  joined date), Quick Actions (frontend
                                  links), System Status (env, Laravel, PHP,
                                  DB, timezone).
                                  (route: GET /admin/dashboard, auth required)
      pages/dashboard.blade.php   Same design, kept in sync with
                                  dashboard.blade.php for the pages/
                                  convention.
     auth/login.blade.php        Admin login form (standalone page, no
                                 sidebar). Posts to route login.attempt.
                                 Route: GET|POST /admin/login

   NOTE: backend uses a layout called `sidebar` (not `app` like the
         frontend). New admin pages should @extends
         'backend.layouts.sidebar'.

--------------------------------------------------------------------------------
 components/  — SHARED UI BUILDING BLOCKS (EXTRAS)
   Anonymous Blade components usable as <x-...> tags in BOTH frontend
   and backend views. No database, no logic — pure markup.

     <x-button>  Link or submit button.
                 Props: href (renders <a>) OR type (renders <button>),
                        variant: primary|dark|light (default: primary)
     <x-card>    White rounded container.
                 Props: title (optional heading)
     <x-alert>   Message box.
                 Props: type: error|success|info (default: info)

   Usage example:
     <x-button href="/about" variant="dark">Go</x-button>
     <x-card title="Hello">Body text</x-card>
     <x-alert type="error">Something went wrong</x-alert>

--------------------------------------------------------------------------------
 errors/  — ERROR PAGES (EXTRAS)
   Laravel renders these automatically by HTTP status code.
     404.blade.php  page not found
     419.blade.php  session/page expired (CSRF token mismatch)
     500.blade.php  server error

--------------------------------------------------------------------------------
  welcome.blade.php
    PURPOSE: Default Laravel welcome page (kept as reference only —
             NOT served anymore; GET / now serves the Home landing page).

QUICK RULES (cheat sheet)
================================================================================
 1. Landing-page image?            -> public/frontend/<page>/
 2. File uploaded through the CMS? -> public/uploads/<type>/
                                      (subfolder per project module,
                                       not fixed — see public/uploads/)
 3. New public page?               -> 1) mock data key in PageController
                                         ::mockData()
                                      2) method in PageController
                                      3) route in routes/web.php
                                      4) views/frontend/pages/*.blade.php
                                      5) sections/* if it needs blocks
                                      6) add the link to 'nav' in mockData()
 4. Reused markup (nav, footer)?   -> views/frontend/partials/*
 5. Admin/CMS feature?             -> views/backend/* (+ database)
                                      @extends backend.layouts.sidebar
 6. Tiny reusable UI piece?        -> views/components/*  (<x-...>)
 7. Real DB data replaces mock?    -> Edit ONLY PageController methods;
                                      keep variable names $site/$nav/$page
                                      so Blade files never change.
 8. Never hard-code page content   -> Data always comes from the
   inside Blade?                      controller (mock now, model later).
